# 采购收货响应丢失后的确认

采购单批准后分批收到 2 件，服务器完成库存和流水写入，但浏览器没有收到响应。旧接口再次提交 2 件会再次累计；完成整单后则无法通过原状态检查确认结果。

## 接口和事务

`POST /api/purchase-requests/{id}/receive` 增加可选 UUID `request_id`：

```json
{"received_qty": "2.00", "request_id": "3014691d-a594-4676-970d-60e4de4ca770"}
```

同一采购单、标识、操作人和数值等价数量重试，返回首次成功的相同响应，库存、采购数量、流水不再增加。UUID 大小写及数量尾零归一化。同键换数量或操作人返回 409；另一采购单可使用相同键。完成或取消订单后，已成功的原请求仍可确认；首次收货仍遵守状态和权限要求。旧客户端省略或发送 null 标识时继续按每次请求累计。

收到备件写锁后刷新采购状态，再查询成功记录。首次成功将库存、采购数量、入库流水和 `purchase_receipts` 快照在同一事务提交；失败不占用标识。去重表有采购单/标识唯一约束和流水唯一约束。同键并发在 SQLite 和 PostgreSQL 上验证只记账一次。响应是首次快照；查看最新库存和状态须另行 GET。

## 浏览器恢复

当前账户与采购单分别保存待确认 UUID 和原数量，首次 POST 前必须成功写入 localStorage。失败保持弹窗，数量不能更改；关闭、刷新或重新登录同一账户后重新打开详情，选择“确认上次收货”。即使整单完成，仍保留确认入口。成功确认才清除匹配的标识，下一批真实到货生成新标识；不会自动后台重试。

存储不可写或待确认数据损坏时停止发送。人工放弃必须先核对采购单及库存流水，并确认提示：原请求可能已入库，下一次将作为新到货。账户之间不会自动重发彼此的记录。旧标签页始终确认自己显示的原标识，另一标签页的新记录不会被确认或放弃动作清除。账户或登录凭证已变化时要求先刷新并回到原账户，请求使用校验过的账户凭证。

清除浏览器数据、更换浏览器、旧客户端或两个标签页同时创建全新请求不能靠服务端猜测为同一业务意图；请先核对流水。同数量的两批真实到货应使用不同标识。

## 升级、验证与范围

正式启动前在维护窗口备份，执行 `python -m app.migrate upgrade` 和 `python -m app.migrate check`。新 HEAD 为 `0003_purchase_receipts`，新增第十五张表；冻结的 0001/0002 与原十四表合同保留。上一版 0002 数据库升级保留已有行；当前版本缺表或旧版本结构漂移拒绝，DDL 失败回滚表、版本及数据。旧备份恢复后先检查/升级，再接入当前应用。代码回退不能替代数据库恢复，禁止自动破坏性降级。

自动测试实际丢弃服务器已成功提交的 HTTP 响应，刷新浏览器复用标识，确认 stock=12、received=2、ledger=1；随后新批次继续正常累计。另有两个真实标签页的确认/放弃与账户切换回归，以及真实 PostgreSQL/SQLite 的并发同键、冲突、权限、快照、回滚和迁移回归。

取消/审批等既有状态入口与首次收货竞争已在后续轮次统一串行化，见[状态竞争说明](PURCHASE-STATE-CONSISTENCY.md)；过时绝对盘点已有[库存版本保护](STOCKTAKE-SNAPSHOT.md)。采购创建与自动补货的精度/金额、超量收货政策和物料编号仍留待后续迭代。本轮结果不代表现场容量验证或跨系统 exactly-once。
