# 库存并发：避免领料成功却漏扣库存

2026-10-03。本轮基于设备点检 PR #9 的候选提交 `8b86c084032a446d065cd64b54759e3e50c5d8bc`，没有数据库迁移或历史数据改写。

## 复现与修复

原库存 10 件，两个请求同时各领 7 件，旧实现都返回成功，库存只剩 3 件，流水却记了两次领用。两次各领 3 件也只扣一次；两次入库和采购到货与领用交错同样会丢失更新。

根因是请求都使用等待写入前读取的 ORM 库存值。仅检查“库存足够”或仅给采购收货加锁，无法协调所有库存写入口。

出入库与采购收货现在共用备件写锁：先对备件执行不改变时间字段的 UPDATE，再重新读取库存。PostgreSQL 在事务结束前持有行锁；SQLite 串行化写事务。拿锁后才校验库存、更新库存和插入流水，避免先插入外键记录再升级锁。

采购收货拿锁后还会刷新采购单，完成的采购单不能根据旧状态重复入账。采购累计数量使用 Decimal 运算，保留原有 JSON 数值输入和响应格式。

## 可以讲的取舍

“如何确认这个修复有效？” 用两个线程同步到旧库存读取位置，刻意重叠真实 API 请求；检查响应、实际库存、流水和采购单，而不是只检查函数调用次数。库存 10、两次领 7 现在只允许一次成功，库存 3 且只有一条流水。

“数据库提交失败会怎样？” 对流水添加真实拒绝约束或 SQLite 触发器，确认库存、采购状态和流水一起回滚；解除拒绝后原请求可以成功。

“是不是所有库存问题都解决了？” 本轮只验证出入库和采购收货的指定并发场景。部分到货重传仍会作为新的收货累计，不提供幂等键；取消/审批与收货竞争未统一协调。ADJUST 仍是绝对值设置，不保护过时盘点快照；超量收货规则和新物料编号竞争留待后续核查。

代码可以 revert 本轮提交，无新增 schema；回退会恢复旧并发风险，也不会修复历史上可能已经产生的库存与流水差异。历史数据需另行核对。

## 后续迭代：数量边界与盘点归零

基于候选 `f6efc764fc166a003190925cc633b32600a51256`，在 2026-10-03 补齐库存输入边界。此前三位小数会被数据库静默舍入，SQLite 和 PostgreSQL 对超范围值的处理不同；前端还会把盘点输入的 0 在失焦时改成 0.01。

登记物料的库存、安全库存、单价，修改物料的安全库存、单价，出入库数量及采购收货数量统一要求有限、非负、最多两位有效小数，范围为 `0..99999999.99`，与现有 `Numeric(10,2)` 相符。JSON 数值和十进制字符串均可输入，末尾多余的零（例如 `1.2300`）仍可接受。错误输入返回 422，显式 null 不再作为可写数量；部分更新省略字段仍保留原值。

ADJUST 填写盘点后的绝对库存，可为 0，成功后记录一条零数量盘点流水并更新低库存提示。IN、OUT、采购收货仍要求大于 0，零值返回 400。入库及采购收货在取得备件锁后检查累计库存/收货上限，超过上限返回 400，库存、流水和采购状态不变。前端按类型调整最小值，并提示盘点可归零。

首批新增 API/数据库回归 110 项（SQLite/PostgreSQL 各 55）：修复前 70 failed、40 passed，修复后 110 passed。独立审查进一步发现依赖库的精度检查会受 Decimal context 舍入影响，放行 `1.00000000000000000000000000001`；追加 18 项真实接口回归先全部失败，再使用原始 Decimal 位数检查有效小数位。库存新增回归共 128 项。新增 Chromium 真实页面回归先捕获盘点 0 被改成 0.01，再验证 UI 提交、实际库存和盘点流水。完整测试及远端检查的最新结果见发布基线说明。

本轮不修改表结构或批量修正历史数据，也没有补齐采购申请创建/自动补货的精度与金额边界、超量收货业务政策、盘点快照版本或收货请求幂等键。回退会恢复输入舍入与盘点归零缺陷。
