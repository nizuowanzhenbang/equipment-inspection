# PP-040/041 设备缺陷到安全隐患的可靠交付

跨 equipment-inspection 与 plant-safety 两个独立数据库。用户授权延长/扩大同批工作；只针对 CRITICAL 缺陷联动，不改变缺陷健康度、验收或安全整改期限规则。

## 发送端 PP-040

- 新 safety_outbox(defect_id 唯一、payload JSON、created_at) 在缺陷本地事务中保存不可变消息，网络调用在缺陷提交后进行。缺陷/设备后续修改不改变重试内容。
- 历史 PENDING/FAILED 且没有消息时，先按缺陷锁创建并提交快照，之后再投递。具有有效隐患引用的现有 SYNCED 不回填/重推；无引用的历史假成功不能跳过确认；未配置端点/非 CRITICAL 保持 SKIPPED，并保留可见原因。
- 手动与调度重试共用 push_one，先串行锁定缺陷、刷新最新状态，避免同时完成/增加尝试。可重发但依赖接收端自然键防重，不能声称跨库 exactly-once。
- 只有 HTTP 200、业务 code=200、正整数 id、非空 hazard_no，及匹配 source_system/external_no 才成功。空/畸形/错误身份回执、重定向、409、服务错误、断网均 FAILED，不伪造成功。错误记录仅类型/状态/受控原因，不保存远端响应或请求凭证。
- 返回前提交真实状态；ACK 本地保存失败回滚并返回非成功，保留已提交消息供重试，不把未保存状态当成功。尝试数是已提交次数，DB 保存失败的网络尝试可能不计入，不能当作全部网络请求的精确总数。进程重启后重试读取保存的消息。部署先更新接收端，再更新发送端。

## 接收端 PP-041

- source_system/external_no 非空且最多 50 字符；severity 仅 MINOR/MAJOR/CRITICAL，大小写归一；标题/人员等按既有列边界校验，不接受任意未知级别降级。现有密钥鉴权保持。
- 新 integration_receipts 表具有来源+单号唯一约束，保存规范化完整请求内容与关联 Hazard。收据与隐患同事务提交。同键同内容返回原隐患，变更内容 409，不改已有隐患/截止期限；业务空值/时间采用统一规范化后比较。
- 接收竞争必须由数据库唯一约束决定；同键同时请求只能生成一张隐患，事务失败不留下收据或半张隐患。不同键的隐患编号碰撞有限重试，达到上限返回可重试 503，不误报成功。
- 历史已有外部隐患无收据时，仅在现有可核对的映射字段与请求一致时建立接续收据；有重复历史键或不一致时 409 并要求核对，不任意选第一条、不批量清洗。
- ACK/反查提供 id、hazard_no、source_system、external_no，供发送端核对。整改仍从 reported_at 起算重大 14/一般 30 天；sla_deadline 不延长安全期限。
- 通过既有 Base.metadata.create_all 增加独立收据表，不重写历史 Hazard；导入在建表前完成，文档说明先备份与维护窗口启动。

## 验收与范围

真实两个应用/独立数据库，通过临时 localhost HTTP 对接，验证正常、接收提交后响应丢失、进程/Session 重新打开、内容修改后重发、重复/冲突、空回执和服务失败。各自 SQLite 与设备 PostgreSQL 本地/CI 竞争；安全接收端也新增真实 PostgreSQL 测试/CI。人工修改已建隐患后相同原始消息重放仍返回原 id，不倒写人工处置。不是现场、真实第三方、容量或跨数据库恰好一次验收。
