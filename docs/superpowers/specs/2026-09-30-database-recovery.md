# 第 3 轮：版本迁移与恢复

用户已要求按路线进入下一轮，并授权代做常规决策。本轮保护现有数据，将隐式启动 DDL 改为显式、可重复的版本升级，提供恢复到独立空库的证据。

## 迁移

- Python 3.11、SQLAlchemy 2、SQLite 与 PostgreSQL 16；采用 Alembic，冻结基线结构，不从未来 ORM 动态生成旧版本。
- 支持空库、上一轮完整未版本化库、上一轮 bootstrap 仅 users/audit_logs 的库，以及完整表集仅缺少两票 signatures 列和/或点检任务测点唯一索引的旧库。
- 升级前验证表、列类型/长度/可空性、主键、外键和索引；未知差异、重复点检记录、未知版本先拒绝。只增加已知缺项，不删除或猜测改写数据。
- 正式启动要求数据库处于目标版本且结构匹配；不自动修改数据库。演示空库与种子通过同一迁移入口升级。bootstrap 要求先迁移，保留前轮独立初始化并发语义。
- 提供 `python -m app.migrate upgrade` / `check`。升级和验收在同一事务，SQLite 显式 BEGIN IMMEDIATE，PG 事务 advisory lock；迁移与其他进程写入需在维护窗口隔离。
- 不提供破坏性自动 downgrade；代码回退与备份恢复分开。

## 备份恢复

- `app.backup` 独立工具：SQLite 使用 backup API，PostgreSQL 使用官方 pg_dump/pg_restore；不复制运行中 SQLite 数据文件。
- 备份文件和清单拒绝覆盖；清单包括散列和一致快照表行数，不包含连接凭证。PG 用导出快照对应 pg_dump --snapshot。
- 恢复显式指定目标，SQLite 文件须不存在，PG 目标须独立且为空；拒绝覆盖源库或已有数据。校验散列和恢复表行数、外键关系，报告可复核。
- 只读取备份来源，恢复仅写新建的隔离目标。工具退出状态不能替代业务验收：测试恢复后继续执行真实 API 点检—派工—修复—验收。
- 不声称全局角色、对象存储附件、部署密钥或全部外部系统均被数据库备份覆盖。

## 验收

先写失败用例。SQLite 与 PG 覆盖空库/旧库升级、幂等、未知结构拒绝、重复记录保留、恢复不覆盖与损坏备份拒绝；恢复后校验核心数据并继续业务流程。运行完整后端、Ruff、既有演示、前端 CI，独立审查，修复重要发现后推送依赖 #6 的 PR。
