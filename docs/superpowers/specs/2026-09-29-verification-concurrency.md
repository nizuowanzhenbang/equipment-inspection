# 第 1 轮：缺陷验收与点检一致性

按已批准的长期路线第 1 轮推进，基于第 0 轮提交 f07a5ed。使用真实 PostgreSQL 复现并修复同缺陷重复验收、不同缺陷验收以及点检/验收交错，不修改 API 请求结构或历史数据。

## 行为与实现约束

- 一个 REPAIRED 缺陷只能完成一次通过或驳回；后来的相同/冲突请求沿用状态错误 400，不再产生健康度或审计副作用。
- 不同缺陷通过验收时，健康度按各次实际执行顺序累加，上限 100；只有 NULL 使用原来的恢复默认 0。
- 点检和验收共享同设备写入顺序，防止旧健康度/设备状态覆盖新结果。
- 只在没有其他未结缺陷且设备处于 MAINTENANCE 时恢复 RUNNING；显式排除当前验收缺陷，不依赖 autoflush。
- 写入异常时缺陷状态、设备健康度、设备状态及审计整体回滚。
- 设备行锁在新增缺陷之前获取，避免 PostgreSQL 外键锁升级死锁；点检先锁任务再锁设备，验收锁设备后重读缺陷，手动上报加入设备写入顺序。
- 等锁后必须刷新 ORM 旧对象；保留第 0 轮数据库原子扣分。

这是现有流程的有界修复。手工编辑设备状态、调度器批量状态扫描和其他管理路径的完整并发语义不在本轮保证范围内。现场生产吞吐和跨系统交付不属于验收结论。

## 验证与交付顺序

先新增/运行失败用例，保留实际失败结果；然后最小修复并跑全量。并发测试在获得业务写锁之前同步最初的读取，不能在持有同一设备锁之后用双请求屏障阻塞。

1. tests/postgresql/concurrency.py 提供独立请求、初始读取同步、单次读取暂停；pg_context 增加真实主管账户。
2. 新增 tests/postgresql/test_verification_transactions.py：同缺陷双通过/通过驳回，不同缺陷双通过，两个方向的点检验收交错，其他未结缺陷，0/NULL/上限和失败回滚。
3. app/utils/transactions.py 增加设备写锁与刷新；tasks.py、defects.py 在相关写入入口使用。
4. 独立审查；后端全量、Ruff、既有演示和 GitHub CI；在前一轮分支上建立单独 PR。

每一步以真实结果记录在 docs/VERIFICATION-CONCURRENCY.md。用户已要求推送并进入本轮，不另加个人学习验收。
