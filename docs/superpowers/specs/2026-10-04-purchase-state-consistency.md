# 采购状态转换与收货串行化

目标：同一采购单的取消、提交、审批、驳回、推送和收货不能依赖等待前的旧状态覆盖已经提交的转换。保留部分到货后取消与成功收货 UUID 重放；不把合法先后两次操作误判为重复。

基线为 main `04f898fb63f4b389f95eba264eff3b7138850870`。用户持续授权自主设计、测试、审查、推送与验证后的合并；沿用单代理执行和一次最终独立审查。

## 方法与接口

复用现有备件事务写锁，所有已有采购状态 API 先查询采购单以得到备件 ID，取得备件锁，再 populate_existing 重新读取采购单。内部 `_lock_pr(db:Session,pid:int)->PurchaseRequest` 提供刷新后的单及备件关系；不存在的采购单/备件返回 404。调用前没有业务 ORM 修改，锁顺序始终备件先、采购后。收货复用同一入口，稳定键匹配仍在首次状态检查前、鉴权之后。

JSON、角色、状态规则不变：DRAFT 才能提交；SUBMITTED 才能批准/驳回；APPROVED 才能推送；APPROVED/SENT 才能首次收货；RECEIVED/CANCELLED 不可取消。无效转换仍 400。合法部分收货后取消仍成功，不逆转已入库数量/流水；原成功 UUID 可继续确认。

审批、推送的状态和对应审计同一事务提交，审计失败则状态/元数据/审计全部回滚。`push_request(db,pr)` 仅更新传入 ORM，不自行提交；调用 API 写审计并唯一提交。该函数目前只有此 API 调用，不扩展新客户端或后台任务。

## 竞争与验收

- 取消先提交，旧读取的 submit/approve/reject/send/receive 必须拒绝，不复活取消单。
- 最后一次收货 5 件先完成，旧读取取消必须 400，stock=15、received=5、status=RECEIVED、ledger=1、成功快照=1。
- 部分收货 2 件先完成，旧读取取消仍可成功；stock=12、received=2、status=CANCELLED、ledger=1，重放同键仍 200 且不再记账。
- 同时批准/驳回、重复提交/取消/推送仅一项符合原状态规则；等待方使用新状态校验。审批成功仅一条审计。
- 不同采购单共享备件锁，同一备件库存入口沿用现有顺序；失败不遗漏解锁，真实 SQLite/PG 回归覆盖。
- 真实审计约束失败验证状态及元数据不泄漏，解除后原操作可以成功。
- 外部推送使用本地 HTTP 测试服务验证真实请求/成功、失败及与收货竞争，不连接真实采购系统。

## 取舍与范围

新建采购及调度器自动补货、金额/数量精度、编号分配、过时 ADJUST 不在本轮。没有迁移、依赖升级或历史数据批改，HEAD 保持 0003。

同步外部推送在现有 `PROCUREMENT_TIMEOUT_SEC`（默认 5 秒）内持有备件锁，会延迟同备件其他写入；服务端 DB 锁超时或网络失败仍按现有错误处理，不宣称请求耗时上限。外部成功后本地提交失败、响应丢失及外部订单取消通知需要后续持久化投递/去重设计；本地事务不能回滚远端订单。本轮测试与 CI 不代替生产容量/现场验收。
