# 面试演示：弱网点检的可靠重传

## 业务问题

点检员提交异常后，服务器已经创建记录和缺陷，但响应在弱网中丢失。旧实现再次提交会报“已录入”或“任务已完成”，客户端无法确认结果，离线队列不断重试。

## 本次实现

- 业务键为 `(task_id, point_id)`：一项任务的一个测点只能有一条原始记录。
- 相同账户、相同检查内容重传，返回原记录，包括原 ID 和记录时间；任务已完成也能确认。
- 已有记录的内容或录入人不同，返回 HTTP 409；保留原记录，交由人工核对。
- 后端在一个事务内取得任务写锁，再创建记录、缺陷、扣减健康度和完成任务。SQLite 使用数据库写锁，PostgreSQL 使用行锁；唯一索引是额外的数据库保护。
- 离线队列等待 IndexedDB 事务提交后才显示入队成功。网络错误可重试，400/404/409/422 停止自动重试并保留内容；401/403 暂停本批次。
- 队列记录绑定录入账户；只有该账户登录后才自动上传。旧版无账户数据保留待核对，不擅自归属新账户。
- 同一页面的自动和手动同步共用一个进行中的批次；跨页面重放由服务端业务幂等处理。

## 五分钟演示

1. 按 README 准备模拟账户、任务和测点，以 inspector 登录，打开“离线点检队列”。
2. 断网后录入一项异常检查，查看队列仍保留原始数据，恢复网络同步。
3. 在 Swagger `/docs` 以同一账户重复 POST `/api/tasks/{tid}/records`，传入完全相同的内容。响应返回同一个记录 ID。
4. 修改 finding 再提交，得到 409；查看任务记录和缺陷仍只有一份，健康度只扣一次。
5. 新增离线记录后切换账户，查看记录显示“等待原账户”；切回原账户再同步。

服务器已提交但响应丢失的分支、两请求并发分支用自动测试展示，避免手工断网时序的不确定性：

```sh
cd backend
python -m pytest tests/test_record_replay.py -v
cd ../frontend
npm test
```

测试访问隔离数据库，不连接真实电厂或外部系统。文件型 SQLite 并发测试会真实发起两个 API 请求；PostgreSQL 锁语义仍需要目标环境验证，不能据此宣称通过生产并发验收。

## 面试追问与取舍

**为什么使用业务键而非随机 Idempotency-Key？** 这里已有“一任务一测点一记录”的业务约束，业务键可以跨终端识别同一检查。允许多次测量的未来版本应显式引入检查轮次，不能复用此约束。

**为什么必须比较内容和人员？** 仅按测点去重会悄悄吞掉第二位人员的新发现。409 把需要人工判断的冲突暴露出来，自动重试不会覆盖原始事实。

**为什么仅先查询是否存在不够？** 并发请求可能同时查不到，因此需要事务写锁和数据库唯一索引。当前 SQLite 会串行化写入，适用于演示；不能把它描述成高吞吐架构。

**是否保证跨系统 exactly-once？** 没有。此迭代保证本地点检业务写入幂等；安全系统推送仍走既有重试。跨系统更强一致性需要收件方去重和持久化消息交付设计。

**旧数据怎么升级？** 启动时为既有数据库检查重复键并创建唯一索引。发现重复会终止启动、指出一组冲突，不自动删除或改写记录。升级前应备份，在维护窗口人工核对重复记录及关联缺陷。

## 可用于简历的事实表述

> 为设备点检原型实现弱网重传幂等：以任务与测点作为业务唯一键，结合事务写锁、内容冲突校验与 IndexedDB 账户绑定，避免重复创建缺陷和重复扣减健康度；通过 API、并发及离线队列回归测试验证异常路径。

这是个人演示项目。不要把模拟数据写成真实现场接入、真实用户规模或已经取得的经营收益。
