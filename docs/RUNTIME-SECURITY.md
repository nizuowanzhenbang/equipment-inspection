# 运行模式、管理员初始化与角色边界

## 本轮决定

沿用现有 JWT、五类角色与数据库模型。默认正式模式，显式开启演示；管理员由本地命令初始化，避免应用启动分配固定密码。保留既有数据和账号，不在升级中自动删除、改密或提权。

## 两种运行模式

| 配置 | production（默认） | demo（显式开启） |
|---|---|---|
| 固定演示账户 | 不创建 | 创建缺失的五个演示账户，不重置已有密码 |
| JWT 密钥 | 至少 32 字符，拒绝已知项目默认值 | 可使用演示默认值 |
| DEBUG | 必须 false | 可配置 |
| JWT 算法 | HS256 | HS256 |
| 外部联动凭证 | 配置对应联动 URL 时检查长度与默认值 | 保持本地演示兼容 |
| 用户创建/重置密码 | 至少 12 字符、最多 72 UTF-8 字节 | 至少 6 字符、最多 72 UTF-8 字节 |
| seed_data.py | 拒绝，未建表、未写数据 | 允许导入模拟数据 |

配置在加载 Settings 时校验，错误不包含输入值。32 字符检查不能证明随机性，请生成独立随机密钥。`SIGNATURE_SECRET` 留空时沿用 JWT 密钥；单独提供时也校验。没有启用的外部联动无需填凭证。

项目 `docker-compose.yml` 仍是带公开数据库和 MinIO 示例密码的**本地演示编排**，现在明确设置 `APP_MODE=demo`。本轮未将它变成可直接公开部署的生产编排。

## 本地演示

在 backend 目录，首次运行可将 `.env.demo.example` 复制为 `.env`。已有 `.env` 时手动加入 `APP_MODE=demo`，不要覆盖其余设置。

```sh
python seed_data.py
uvicorn app.main:app --port 8003 --reload
```

五个演示账户及密码见 README。登录页面使用通用提示，不把演示凭证当作所有环境的默认账户。`python interview_demo.py` 会自行显式选择 demo，并继续使用隔离临时数据库。

种子冒烟测试另外复现了原脚本的重复单号：关闭 autoflush 时，多条未提交缺陷均读取同一计数。新种子改用 UUID 缺陷单号；测试验证 5 用户、18 设备和 8 个不同缺陷编号。

## 正式模式初次启动

在独立的 backend 工作目录中参考 `.env.production.example` 配置环境。示例中的空密钥会故意使校验失败。可在本地生成密钥并保存到受控 `.env` 或部署密钥存储，不提交 Git：

```sh
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

配置 `APP_MODE=production`、新的 `SECRET_KEY`、目标 `DATABASE_URL`、实际前端 `ALLOWED_ORIGINS`。`SCHEDULER_ENABLED=false` 是示例初值，可在确认调度策略后开启。

```sh
python -m app.bootstrap_admin --username operator
uvicorn app.main:app --port 8003
```

初始化命令在终端隐藏输入并确认密码。自动化可使用 `--password-stdin` 从受控管道输入一行；不要将密码写入命令行参数、脚本正文或共享日志。

- 创建 User 和 AuditLog 所需表，其余表由现有应用启动流程创建；正式版本迁移仍待下一轮。
- 同名活跃管理员已存在：成功返回“未改变”，不重置密码，也不重复记审计。
- 同名普通/禁用账户：拒绝；已有其他管理员（含禁用）：拒绝，后续通过管理员用户管理创建账号。初始化命令不是账户恢复入口。
- 首次创建与 `user.bootstrap` 审计在同一事务提交；审计写入失败则账户回滚。
- SQLite 使用 BEGIN IMMEDIATE，PostgreSQL 使用事务 advisory lock，将建表和账户创建一起序列化。空库和已建表库上的两个并发初始化只产生一个管理员和一条审计；需在启动应用之前完成初始化，应用启动建表不参与此锁协议。
- 支持 SQLite 和 PostgreSQL。本轮没有修改既有账号、密码或角色的历史数据。

## 接口角色矩阵

| 操作 | ADMIN | INSPECTOR | REPAIRMAN | SUPERVISOR | VIEWER |
|---|---|---|---|---|---|
| 点检录入 | 允许 | 允许 | 拒绝 | 拒绝 | 拒绝 |
| 派工/验收 | 允许 | 拒绝 | 拒绝 | 允许 | 拒绝 |
| 开始维修/提交修复 | 允许 | 拒绝 | 允许 | 拒绝 | 拒绝 |
| 用户目录/创建/编辑/改密/启停 | 允许 | 拒绝 | 拒绝 | 拒绝 | 拒绝 |

矩阵使用真实密码登录、JWT、数据库查询和有效业务对象，不替换角色依赖。拒绝返回 403，并检查业务记录和审计无副作用；已禁用账户的旧 token、伪造 token 和未登录请求不能访问用户管理。管理员不能禁用或降级自己，即使用户名不是 admin。

前端创建和重置密码均采用 12 字符及 72 UTF-8 字节限制，在两种模式中都可提交；演示 API 保留较短密码兼容。中文等多字节输入也有后端回归覆盖。

`GET /api/users` 从“任意已登录用户”收紧为 ADMIN，属于有意的权限兼容变化。当前前端只有管理员用户管理页使用此接口。未来人员选择应设计仅返回必要字段的专门目录接口。

## 升级与限制

1. 默认运行模式变化可能使原来零配置启动失败；本地演示必须显式选择 demo，正式运行需补齐密钥。
2. 已有演示库的固定密码不会被模式切换消除。保留备份后检查旧账户，由合法管理员处理，不把切换模式当作凭证迁移。
3. 更换 JWT 密钥会使旧 token 失效。既有电子签名若使用旧密钥，换密钥后也可能无法验证；本轮没有实现历史签名密钥轮换或重新签署。已有签名数据的部署须单独规划迁移。
4. 这里只覆盖指定角色权限，不保证“仅被指派人员可操作”、多管理员并发禁用的最终管理员保留，或所有接口的权限审计。密码重置目前不单独撤销既有 token；禁用账户会在后续鉴权时拒绝。
5. 登录限流、MFA、凭证轮换、生产基础设施和完整数据库迁移另行推进，不将这些测试表述成生产安全认证。

代码可 revert 本轮提交，但默认账户创建行为也会随旧代码恢复。切勿在正式环境无评估回退到自动创建固定账户的旧版本；账号和审计数据不会随代码回退删除。

## 验证入口

```sh
cd backend
python -m pytest tests/test_runtime_security.py tests/test_role_boundaries.py -q
# 配置独立 TEST_POSTGRESQL_URL 后：
python -m pytest tests -q
```

PostgreSQL 附加用例覆盖同名及异名的并发管理员初始化、审计约束失败导致账户回滚及重试。全量仍包含前两轮的点检/验收并发回归、离线重放和 API 面试演示；最终计数与 CI 链接以 PR 为准。
