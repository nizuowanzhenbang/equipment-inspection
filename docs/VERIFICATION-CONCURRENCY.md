# 验收与点检并发一致性

## 复现结果

在第 0 轮提交 `f07a5ed` 上新增 12 项真实 PostgreSQL 验收测试，修复前 6 项失败、6 项通过：

| 场景 | 旧结果 | 修复后要求 |
|---|---|---|
| 同一缺陷双通过或通过/驳回竞争 | 两个请求都返回 200 | 一个 200，一个状态错误 400；仅一次审计和一次有效处理 |
| 两个缺陷分别验收 | 健康度 80 → 83 | 80 → 86，最后一个未结缺陷关闭后恢复运行 |
| 验收先读、点检先提交 | 验收用旧 80 加分到 83 | 80 − 3 + 3 = 80，保留新未结缺陷对应的检修状态 |
| 严重异常先读、验收先提交 | 点检按旧检修状态跳过更新，最终仍运行 | 验收恢复运行后，严重异常重新转检修；分数 80 + 3 − 8 = 75 |
| 开启 autoflush，另有一个未结缺陷 | 提前恢复运行 | 明确排除自身后检查其他缺陷，保持检修 |

用例使用各自的数据库连接、API 请求及真实 JWT 用户。查询屏障控制最初读取的重叠；单次读取暂停控制交错，不替换业务代码或数据库结果。

## 事务顺序

1. 点检先获取任务写锁，再在生成异常缺陷前获取设备写锁。
2. 手动缺陷上报在插入缺陷前获取设备写锁。
3. 验收获取设备写锁，再刷新缺陷并校验是否仍为 REPAIRED；设备对象也重新读取。
4. 缺陷、分数、设备状态及审计在同一事务提交；失败时一起回滚。

`lock_equipment` 使用 `updated_at = updated_at` 的 UPDATE：PostgreSQL 锁定设备行，SQLite 串行化写入；不会人为改写更新时间。先锁设备再插入关联缺陷，避免两个外键持锁事务同时升级设备写锁。锁释放后 ORM identity map 不会自动变新，所以显式使用 `populate_existing()`。

点检保留数据库内原子扣分，验收在设备锁内基于刷新后的分数加分并限制到 100。NULL 的恢复初值仍为 0，点检扣分的 NULL 初值仍为 100；这是原业务规则的保留。API 请求与历史数据不变，不需要数据库结构迁移。重复验收保留既有 400 状态错误，并非幂等成功响应。

## 取舍与边界

同设备写入会排队，换取这三个路径之间可解释的事务顺序；不同设备仍能并行。没有测量生产吞吐量。本轮不保证取消、派工、维修提交、设备直接编辑、工作票或调度批处理与验收之间的所有交错；这些路径仍需独立状态机并发设计。默认验证 PostgreSQL READ COMMITTED 隔离级别。

测试使用隔离 schema 和模拟设备，不代表现场部署、浏览器端到端验收或跨系统 exactly-once。前一轮 PR 应先合并，再将本轮 PR 的目标切换到 main。代码回退可通过 revert 本轮提交完成，既有业务数据不会自动回退。
